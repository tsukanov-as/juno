# Консоль и окружение

`Консоль` / `Console` — глобальное свойство OneScript, тип `Консоль` / `Console`,
а не конструктор. Реализация использует потоки текущего `ApplicationContext`.
Сигнатуры соответствуют описанному поднабору OneScript 2.2.1.

| RU / EN | Контракт |
|---|---|
| `ПрочитатьСтроку()` / `ReadLine()` | строка без разделителя; пустая строка `""`, EOF — `Неопределено` |
| `Вывести(Текст)` / `Write(Text)` | преобразование через `Строка`, без перевода строки |
| `ВывестиСтроку(Текст)` / `WriteLine(Text)` | как Write, затем системный перевод строки: LF на Unix, CRLF на Windows |
| `КодировкаВходногоПотока` / `InputEncoding` | чтение и запись кодировки stdin |
| `КодировкаВыходногоПотока` / `OutputEncoding` | чтение и запись кодировки текстового stdout |
| `ОткрытьСтандартныйПотокВвода()` / `OpenStandardInput()` | raw stdin, тип `Поток` / `Stream` |
| `ОткрытьСтандартныйПотокВывода()` / `OpenStandardOutput()` | raw stdout |
| `ОткрытьСтандартныйПотокОшибок()` / `OpenStandardError()` | raw stderr |

Write/WriteLine требуют ровно один аргумент; `Неопределено` и `Null` означают пустой текст.
Остальные перечисленные методы не принимают аргументов. Вывод немедленно сбрасывается в host stream;
ошибка `PrintStream.checkError()` (например, broken pipe) становится ошибкой программы.

По умолчанию текст идёт в UTF-8 **без BOM**. Кодировка задаётся значением `КодировкаТекста`
или именем: UTF-8, UTF-16LE, windows-1251, IBM866. `Системная` выбирает UTF-8, ANSI — 1251,
OEM — 866. Getter возвращает канонический enum: UTF8БезBOM, UTF16, ANSI, OEM.
Даже `OutputEncoding = TextEncoding.UTF8` не пишет BOM. Другие кодировки явно отвергаются.
Некорректные/незавершённые байты ввода и непредставимые символы вывода вызывают ошибку;
OneScript в некоторых таких случаях заменяет символы на U+FFFD/`?`.

В `run` и автономном JAR `Сообщить` сохраняет вывод в stdout с системным EOL и учитывает
`Console.OutputEncoding`. Диагностика компилятора/необработанных ошибок идёт в stderr.
Код `ЗавершитьРаботу(N)` сохраняется и в run, и в JAR; необработанная ошибка даёт 3.
Сборка не пишет служебных сообщений в поток исполняемой программы.
Кодировка raw-потоков и диагностики от OutputEncoding не меняется.
Java-host с собственным message sink продолжает сам управлять маршрутизацией сообщений;
сообщения фонового задания остаются в его буфере сообщений.

## Текст и raw-байты

ReadLine распознаёт CRLF, LF и отдельный CR; последний текст без EOL возвращается перед EOF.
**Входной BOM сохраняется как U+FEFF**, подобно проверенному OneScript Console, в отличие от
файлового TextReader. Чтение использует общий byte cursor без read-ahead и скрытого reader thread.
Разные raw wrappers и текстовая консоль читают одну последовательность, не теряя буферизованные байты.

CR завершает строку немедленно, без блокировки ради следующего байта. Следующий ReadLine
пропускает возможный LF. Если следующим идёт raw Read, он получает все оставшиеся байты,
включая этот LF; нулевой raw Read не меняет состояние. Это явный контракт смешивания,
не обещание совпадения с буферизацией .NET. Менять кодировку допустимо на границе текстовых
строк/символов; после raw-чтения середины многобайтного символа следующая строка может дать ошибку.
Одна строка занимает память пропорционально её длине; для больших данных используйте chunks.

Стандартный `Поток` имеет `CanSeek = Ложь`, `CanRead`/`CanWrite` по направлению.
Поддержаны `Прочитать/Read(Буфер,Смещение,Количество)` (EOF = 0),
`Записать/Write(Буфер,Смещение,Количество)`, `СброситьБуферы/Flush()` и `Закрыть/Close()`.
Чтение может вернуть меньше запрошенного числа байтов. Seek/CurrentPosition/Size/SetSize
дают явную ошибку. Raw Write сохраняет каждый байт, без BOM, кодирования или замены EOL.

Для текста в stderr без ручного byte buffer используйте поддержанный `BinaryData.Write(Stream)`:

```bsl
Поток = Console.OpenStandardError();
Попытка
    GetBinaryDataFromString("Ошибка" + Символы.ПС, TextEncoding.UTF8).Write(Поток);
Исключение
    Поток.Close(); ВызватьИсключение;
КонецПопытки;
Поток.Close();
```

Это точные UTF-8 bytes без BOM с явным LF; Console.OutputEncoding не влияет на raw stderr.
Тот же `Write` принимает FileStream/MemoryStream и пишет с текущей позиции, не закрывая приёмник;
подробнее — [двоичные данные и потоки](files.md#двоичныеданные--поток).

Close идемпотентно закрывает **обёртку**, и дальнейшие операции через неё запрещены.
Ни Close, ни выход scope/отмена не закрывают host stdin/stdout/stderr. Можно открыть новую обёртку.
Открытые обёртки и объект Console не передаются через ValueCopy между заданиями.

Чтение stdin запрещено в фоновых заданиях и lint, включая `--jobs 1`: host input нельзя
безопасно принудительно закрыть при отмене worker. Ошибка возникает до чтения/создания input wrapper.
Передавайте данные параметром или через файл. Root run/JAR читает stdin синхронно; при встраивании
host отвечает за разблокировку своего InputStream. Аналогично блокирующий OutputStream произвольного
host должен управляться хостом: отмена закрывает только обёртку и не может прервать чужой write/flush.
Параллельные записи синхронизируются по конкретному host stream на время одного Write/WriteLine/chunk.

`Прочитать/Read()` самой Console — клавиатурный API OneScript, падающий при перенаправленном stdin;
juno его явно не поддерживает. Управление терминалом (цвет, курсор, размеры, ReadKey, события),
SetOutput и SetError не поддержаны. Используйте raw stderr, не глобальную замену System.*.

## Переменные среды

| RU / EN | Аргументы |
|---|---|
| `ПолучитьПеременнуюСреды` / `GetEnvironmentVariable` | `(Имя, Расположение = Process)` → строка либо Неопределено |
| `УстановитьПеременнуюСреды` / `SetEnvironmentVariable` | `(Имя, Значение, Расположение = Process)` |
| `ПеременныеСреды` / `EnvironmentVariables` | `(Расположение = Process)` → новое Соответствие |

`РасположениеПеременнойСреды` / `EnvironmentVariableTarget` имеет RU/EN значения
`Процесс/Process`, `Пользователь/User`, `Машина/Machine`. Поддерживается только **Process**;
User/Machine явно отвергаются. Строки/числа вместо enum не принимаются.
Неопределено/пропуск optional target выбирает Process. Пустое значение, Неопределено или Null
удаляет переменную. Имя — непустая строка без `=`/NUL; значение — строка без NUL.

Process означает **виртуальную среду приложения**, изначально копию host environment,
а не изменение `System.getenv()` или среды JVM. Перечисление возвращает отдельную копию;
её изменение не меняет среду. Имена чувствительны к регистру на Unix, без учёта регистра
на Windows (Java `String.CASE_INSENSITIVE_ORDER`, без попытки эмулировать все нативные Unicode-правила).

Задание получает снимок cwd/env и кодировок Console при запуске; последующие изменения
родителя/ребёнка независимы. Host streams и byte cursor остаются общими заимствованными ресурсами.
Каждый Main.execute и каждый независимый ApplicationContext имеют отдельное состояние.
Java embedding: `Main.execute(args, input, printOut, printErr)` принимает stdin без `System.setIn`;
перегрузка без аргумента `input` использует `System.in`. Для управления cwd/env/OutputStream используйте
`ApplicationContext` + `Execution.withContext` + собственный host scope.

## Пример фильтра

```sh
printf 'Привет\n\nмир\n' | JUNO_PREFIX='> ' java -jar build/juno.jar run examples/консоль/Программа.bsl
java -jar build/juno.jar build examples/консоль/Программа.bsl --output filter.jar
printf 'Привет\n' | java -jar filter.jar
cat source.bin | java -jar filter.jar --bytes > copy.bin
```

[Программа](../examples/консоль/Программа.bsl) различает пустые строки и EOF,
читает префикс из среды, выводит верхний регистр или копирует байты chunks по 64 КиБ.


При текстовом выводе одиночный UTF-16-суррогат заменяется U+FFFD (UTF-8),
чтобы `Сообщить(Сред("a😀b",2,1))` не завершало программу ошибкой кодировки.
Raw-вывод передаёт исходные байты.


CLI и самостоятельный JAR тихо завершаются кодом 0, когда получатель закрывает
stdout (например, `| head`). Ошибка записи в отдельный host OutputStream API
сообщается вызывающей Java-программе. `ЗавершитьРаботу` принимает
код 0..255, дробная часть отбрасывается; выход за диапазон даёт явную ошибку.
