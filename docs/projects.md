# Проект, библиотеки и поставка

Команда `java Build.java` создаёт архив `build/juno.zip` без доступа к сети.
Требуется JDK 21+. Архив содержит `lib/juno.jar`, bin, документацию, примеры и плагины.
Исходник `src/Parser.bsl` включён как справочник узлов и подписок для авторов плагинов.
Распакуйте архив в постоянное место. Linux/macOS: `sh /путь/juno/bin/juno --help`
(или `chmod +x bin/juno` и добавьте bin в PATH). Windows PowerShell из папки `juno`:
`.\bin\juno.cmd --help` либо `.\bin\juno.ps1 --help`; полный путь с пробелами
вызывается через `& 'C:\путь\juno\bin\juno.cmd' --help`.
Если политика выполнения запрещает `.ps1`, используйте `.cmd`.
После установки JDK откройте новый терминал (для встроенного терминала перезапустите IDE).
JAVA_HOME выбирает JDK, иначе используется PATH. Launchers проверяют
Java 21+, сохраняют cwd и код выхода. Для приложения достаточно `java -jar app.jar`.

```sh
juno init demo
juno run demo
juno test demo --filter '*Приветствие*' --format json
juno build demo --output app.jar
cd /tmp
java -jar /полный/путь/app.jar
```

В PowerShell вместо `cd /tmp` используйте `Set-Location $env:TEMP`,
а путь к JAR укажите как `java -jar 'C:\полный\путь\app.jar'`.

`init` создаёт manifest, src/Программа.bsl, src/Приветствие.bsl, tests/Smoke.bsl и assets/info.txt.
При наличии любого создаваемого файла команда завершается до записи. Свои исходники не затираются.

```json
{
  "schemaVersion": 1,
  "entry": "src/Программа.bsl",
  "sources": ["src"],
  "tests": ["tests"],
  "exclude": ["src/черновики"],
  "resources": [{"path": "assets", "prefix": ""}],
  "dependencies": [{"path": "../shared", "namespace": "Shared"}],
  "defines": ["Сервер"],
  "requires": {"jdk": 21}
}
```

Пути sources/tests/resources/entry/exclude относительны manifest, разделитель `/`; `..` запрещён.
Исключения — префиксы сегментов, `src/old` не исключает `src/older`; glob не поддерживается.
`./` нормализуется при сравнении. Имена модулей считаются от каждого source root:
`src/Helpers/Text.bsl` → `Helpers.Text`. Namespace проекта добавляется перед именем.
Отсутствующий tests допустим. Состав сборки задаёт только manifest: в `run`/`build` не попадают
пути из `tests`, `exclude` и настроенные lint-`plugins`, а также служебные каталоги `.git`, `.hg`, `.svn`,
`.idea`, `.vscode`, `.juno` (их имена не могут быть модулями). Каталог `src/Tests`, `src/Plugins` или
`src/build` с модулями собирается как обычный. У проекта без `schemaVersion` действует
соглашение по именам: каталоги `tests`/`test`/`тесты`, `plugins`, `build`, `dist`, `node_modules`
на любой глубине не входят в приложение. Исходник — файл `.bsl`; `.os` из OneScript не принимается, переименуйте его в `.bsl`.
Имена native types и классов juno зарезервированы; дубли имён/ресурсов проверяются без учёта регистра.
Ссылки за пределы выбранных корней не следуются. Неизвестные поля/версии manifest — ошибка.
`defines` объединяются с `--define` и принимают только существующие RU/EN символы препроцессора Parser
(например Сервер/Server, НаСервере/AtServer), не произвольные feature flags; проект с `schemaVersion` без defines имеет пустое целевое окружение.

Настройки без `schemaVersion` могут содержать только `plugins` и `params` или быть пустыми (`{}`).
В этом режиме модули считаются от папки manifest, без него — от папки запускаемого файла.
Для `test папка` без manifest корень — эта папка. Остальные поля требуют `schemaVersion: 1`. `lint --config custom.json` читает именно указанный файл.

## Скрипт и соседние файлы

Запускаемый файл — программа, а не класс, поэтому его имя может не быть именем класса: `convert-files.bsl`,
`my script.bsl`, `2024_report.bsl`, `Файл.bsl`, `Консоль.bsl`, `Parser.bsl` запускаются и собираются в JAR
(внутри имя класса подбирается: `convert_files`, `my_script`, `_2024_report`, `Файл_`, `Консоль_`, `Parser_`).
Файл, названный в командной строке, не исключается правилами имён каталогов (`build`, `tests`, `plugins`).

Если у проекта нет `schemaVersion`, `run`, `build` и `test файл.bsl` собирают файл и только модули, чьи имена
он (и затем они сами) упоминают как слово, с учётом регистра не различая: остальные `.bsl` каталога не
компилируются, и ошибка в несвязанном файле не мешает. Файл с именем, которое нельзя написать в коде
(`1lib/x.bsl`), в этом режиме пропускается; файл, чьё допустимое имя занято (`Файл.bsl`, `Array.bsl`, `Parser.bsl`),
пропускается, пока программа его не упомянула, — тогда это ошибка. Для всей папки (`test .`) и для проектов с
`schemaVersion` проверяется каждый файл исходников, и ошибка называет файл. Модуль, имя которого программа
собирает во время выполнения из частей, нужно упоминать целиком или перечислить в `sources` проекта с `schemaVersion`.

## Две программы, одна библиотека

Рабочий пример — `examples/проект`: `app-a` и `app-b` используют неизменяемый shared.

```sh
juno run examples/проект/app-a
juno run examples/проект/app-b
juno test examples/проект/app-a
juno build examples/проект/app-a --output app.jar
```

Библиотека: `{"schemaVersion":1,"namespace":"Shared","sources":["src"]}`;
entry ей не нужен. Программа создаёт `Новый Shared.Helper`. Зависимость библиотеки
может объявлять `Utils`; вызов внутри Shared должен быть `Новый Utils.Tool`.
Namespace транзитивной библиотеки не становится `Shared.Utils`. Совпадающий diamond с тем же
путём и namespace подключается один раз. Цикл, разные aliases одного пути, разные пути для одного
namespace и несовпадение объявленного namespace — ранняя ошибка. Зависимости только локальные,
без загрузки сети и поиска модулей относительно вызывающего класса.

Перенос OneScript: вынесите обычные экспортные BSL-методы в src библиотеки, объявите dependency
с namespace, замените `Новый Класс` на `Новый Shared.Класс`. `#Использовать` и глобальный
`ПодключитьСценарий`/`AttachScript` диагностируются до компиляции с рекомендацией manifest.
Самописный метод с таким именем и обращения через объект допустимы. Динамическая регистрация
классов, загрузчик OneScript и его библиотеки платформенных сервисов не реализованы.

## Ресурсы и диагностика

Собранные модули доступны через [реестр `Модули` / `Modules`](modules.md).
`Модули.Имена()` перечисляет их без создания объектов, `Модули.Получить(Имя)`
возвращает общий экземпляр в текущем контексте выполнения.

Ресурсы перечисляются явно: каталог разворачивается рекурсивно, скрытые/служебные файлы и
BSL из каталога не пакуются. Отдельный файл можно включить явно. Секреты не обнаруживаются:
не перечисляйте их в resources. Имя ресурса = namespace библиотеки с `/` + prefix + относительное
имя файла. Для Shared это `Shared/info.txt`. Имена регистрозависимы при чтении, `..`, `:`, `\\`,
пустые/управляющие сегменты запрещены. `GetResourceText("info.txt", "UTF-8")` возвращает строку,
`GetResource` — ДвоичныеДанные, `ResourceNames` — ФиксированныйМассив. Getter ограничен 16 MiB;
источником в run служит выбранный файл, в JAR — запись архива, независимо от cwd.

JAR включает runtime, модули и ресурсы. При одинаковых входах и toolchain байты повторяются:
порядок, ZIP timestamps и JSON metadata фиксированы, абсолютных путей нет. Требования JDK
всех зависимостей объединяются максимумом и проверяются при запуске JAR. Сборка отвергает
недоступный JDK. Выходы/отчёты не могут затирать входы, config,
исходники или сам runtime; проверяются также symlinks и hardlinks.

Диагностика содержит относительный путь и строку. `ИнформацияОбОшибке().ИсходнаяСтрока` в run
читает snapshot этого запуска; вложенные/параллельные контексты его не разделяют. Обычный JAR
сохраняет только пути модулей, без текста; `--debug-sources` включает текст и восстанавливает
SourceLine. Это осознанное включение исходников в артефакт.

`build --format json|jsonl [--report файл]` пишет build/error record.
`test --format json` пишет массив test records и summary; jsonl — записи по строкам.
Поля теста: schemaVersion, name, status, diagnostics; ошибка содержит causes с type/message/location.
`Message` и console-output тестов идут в stderr при машинном формате, stdout остаётся JSON.
Коды: 0 успех, 1 провал теста/синтаксис, 2 неверные параметры/manifest, 3 runtime/IO/компиляция.
Отсутствие подходящих тестов — ошибка. Экспортные процедуры Test*/Тест* без аргументов выполняются
в свежем объекте и контексте; `--filter` сравнивает полное module.method без учёта регистра, * и ?.
Для прямого `test файл.bsl` допускаются тесты в source-модуле; library entry не требуется.

`Новый Утверждения` / `New Assertions` и `Новый ВременныйКаталог` / `TemporaryDirectory`
описаны в [каталоге API](api.md). Временный каталог автоматически удаляется при завершении
теста; Close удаляет раньше. setup/teardown и JUnit XML не поддерживаются.

Ошибки выполнения, `ОписаниеОшибки()` и `Утверждения.ВызываетИсключение` используют
одинаковый текст: например, «Деление на 0». CLI и самостоятельный JAR выводят
BSL-стек с файлами и строками. Лексические ошибки привязаны к исходнику, ошибки
чтения исходника сообщают о недопустимом UTF-8 без внутренних сообщений JVM.

В диалекте juno `run`, `build`, `test` и `lint` проверяют имена глобальных функций,
переменных и конструкторов до выполнения, включая неисполняемые ветви. Сигнатуры
берутся из реестра runtime; неизвестное имя и неверная арность сообщаются с файлом,
строкой и колонкой. Пользовательские типы разрешаются по модулям проекта. Для
синтаксического анализа кода платформы, использующего её конфигурацию и серверные
API, применяется `lint --dialect 1c`; в этом режиме семантика juno не проверяется.


CLI и самостоятельный JAR исполняют BSL в потоке со стеком 64 МиБ.
Дополнительные JVM-флаги для размера стека не требуются. Переполнение стека
при бесконечной или слишком глубокой рекурсии диагностируется как ошибка BSL.


Если нативная кодировка имён файлов JVM не представляет кириллицу (например,
Linux с LANG=C), `init` использует Main.bsl/Greeting.bsl. Исходный BSL-код и
ресурсы остаются в UTF-8.
