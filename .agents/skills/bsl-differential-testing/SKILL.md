# Сравнение BSL: 1С, OneScript и juno

Получай наблюдаемое поведение эталонов, запускай тот же BSL-код в juno и отделяй
ошибки реализации от осознанных различий контракта. Платформа 1С и OneScript — два
самостоятельных эталона; совпадение с одним не означает совпадения с другим.

## Быстрый запуск

Команды выполняются из корня репозитория и одинаковы на Linux, macOS и Windows
(пути с `/` понимают все оболочки). Python 3 — только стандартная библиотека
(`python3`, на Windows обычно `python` или `py -3`); juno требует Java 21+.
Путей к движкам в командах нет: `compare.py` находит их сам и печатает, что выбрал.

```sh
java Build.java build
python3 .agents/skills/bsl-differential-testing/scripts/compare.py --cases .agents/skills/bsl-differential-testing/assets/collections.json
```

Порядок поиска каждого движка: аргумент → переменная окружения → типовое место →
`PATH` → каталог установки (из нескольких версий берётся старшая). Выбранный путь,
источник и SHA-256 попадают в отчёт (`tools`).

| Движок | Аргумент | Переменная | Где ищется дальше |
|---|---|---|---|
| Платформа 1С | `--platform` | `ONEC_PLATFORM_BIN` | Windows: `%ProgramFiles%\1cv8\<версия>\bin\1cv8.exe`; Linux: `/opt/1cv8/x86_64/<версия>/1cv8`; macOS: `/opt/1cv8t/<версия>/1cv8t` |
| OneScript | `--oscript` | `ONESCRIPT_BIN` | `PATH` (`oscript`); Windows: `%ProgramFiles%\OneScript\bin`; Linux: `/opt/oscript/bin` |
| Java 21+ | `--java` | `JAVA_BIN` | `JAVA_HOME/bin/java`, затем `PATH` |
| JAR juno | `--juno` | `JUNO_JAR` | `build/juno.jar` в корне репозитория |

Если движок не найден, запуск останавливается с подсказкой, а не пропускает его
молча. Подробности установки у вас могут отличаться — тогда задай аргумент или
переменную. Если движок недоступен или API в нём отсутствует, явно выбери доступный
набор через `--engines` (нужно минимум два) и укажи непроверенное покрытие в выводе
пользователю. По умолчанию запускаются **все четыре** режима. Отчёт пишется в
`report.json` во временном каталоге запуска; `--output <файл>` сохраняет его
по указанному пути. Отчёты экспериментов храни вне репозитория.

Глобальные regex-функции 1С отсутствуют в установленном OneScript 2.2.1;
не подменяй их проверку классом регулярных выражений с другим API:

```sh
python3 .agents/skills/bsl-differential-testing/scripts/compare.py --cases .agents/skills/bsl-differential-testing/assets/regex.json --engines platform juno jar
```

## Рабочий порядок

1. Прочитай контракт нужного API в `docs/` и регрессионные тесты в `tests/`.
   Для выбора проверок и сложных сценариев см. [стенды и диагностику](references/existing-harnesses.md).
   Реальный запуск имеет приоритет над предположением о поведении; справка помогает
   выбрать кейсы, но не заменяет запуск.
2. Составь независимые кейсы: обычный результат, границы, пустые значения,
   ошибки аргументов, изменения состояния и связи объектов — по смыслу API.
   Добавляй случаи из контракта и известных рисков, а не зеркальные копии реализации.
   Формат и правила снимков: [написание кейсов](references/cases.md).
3. Собери текущую juno, запиши наблюдения эталонов и сравни CLI/JAR. Для экспериментов
   и отчётов используй временный каталог вне репозитория. Кейсы, которые должны
   проверяться регулярно, добавляй в assets этого скилла или регрессионные тесты.
4. Разбери каждое отличие. Если 1С и OneScript расходятся, выбери контракт явно:
   для API происхождения 1С предпочитай проверенное поведение платформы, если нет
   обоснованного решения juno; для специфического API OneScript проверяй OneScript.
   Учитывай стоимость переноса кода, но не воспроизводи зависания или случайные баги
   движка ради формального совпадения.
5. Ошибку juno исправь и закрепи адресным регрессионным тестом. Осознанное отличие
   зафиксируй с ID кейса, версиями, наблюдениями всех движков, выбранным результатом
   juno и причиной. Если добавляешь допуск в специализированный компаратор, проверяй
   конкретный ожидаемый результат juno; исключение по одному ID не должно пропускать
   любое будущее поведение. Не переписывай эталон на результат juno.
6. Повторно выполни изменённые кейсы и нужные проверки проекта. Сообщи, какие движки,
   версии, контексты и кейсы реально запускались, какие отличия приняты и что осталось
   непроверенным. Не объявляй полную совместимость по ограниченному набору.

## Как работает общий запускатель

- Создаёт новый каталог через `tempfile.mkdtemp`; пользовательские базы не открывает.
- В 1С создаёт **новую** файловую базу, выгружает пустую конфигурацию, добавляет серверный
  общий модуль и вызов при старте управляемого приложения, загружает конфигурацию,
  запускает `ENTERPRISE`. Это реальная платформа, а не OneScript и не эмуляция.
- Код функций кейсов общий для всех режимов; отличаются только точка входа и путь
  вывода. Контекст эталона 1С — серверный общий модуль файловой базы. Клиентские,
  интерфейсные и конфигурационно-зависимые API требуют другого стенда.
- В OneScript выполняет `Probe.os` (его родное расширение); в juno выполняет `Probe.bsl` через `run`
  и отдельно собирает JAR. При запуске JAR исходный `.bsl` переименован, рабочий каталог другой. Исходник
  сохранён как артефакт вне имени/расширения, использовавшихся при компиляции.
- Сохраняет BSL, JSON каждого движка, последнюю начатую пробу, stdout/stderr,
  команды, SHA-256 входов и исполняемых файлов. Версии Java/OneScript — в логах
  `version.*`; версию 1С дополнительно указывай из проверенной установки, один хеш
  или имя каталога не доказывают номер версии.
- Пишет JSON после каждой завершённой пробы. Таймаут ограничивает каждую команду
  (45 секунд по умолчанию, `--timeout`); результат без полного набора — `INCOMPLETE`.
  Временный каталог сохраняется для разбора; путь есть в отчёте и выводе.

Коды выхода: **0 — MATCH**, **1 — DIFFERENCES**, **2 — INCOMPLETE**
(ошибки аргументов также дают 2). `MATCH` означает совпадение выбранных наблюдений,
а не одобрение контракта и не корректность алгоритма относительно предметной задачи.
Сравнение попарное, автоматического выбора «правильного» эталона нет.

## Важные ограничения

- Весь набор компилируется одним модулем. Отсутствующая глобальная функция или ошибка
  синтаксиса может остановить набор до выполнения `Попытка`. Это `INCOMPLETE`, а не
  ожидаемая ошибка кейса. Изолируй пробу через `--case <id>`; при отсутствии API
  вынеси её в отдельный набор/профиль и сохрани наблюдение о неподдержке.
- Возвращай JSON-совместимый **снимок** результата. Коллекции, даты, UUID, бинарные
  значения и regex-результаты преобразуй явно, не проверяй одновременно непреднамеренно
  ещё и сериализацию движка. Если проверяешь сериализацию, верни её результат строкой.
- Обычные результаты сравниваются точно, порядок массивов значим. Числа читаются
  без потери десятичной точности; булево не равно числу. Текст ошибок сохраняется,
  но автоматически сравнивается только статус `error`. Одинаковая ошибка на всех
  движках не доказывает, что проверяемая операция была достигнута: проверь текст
  и поставь операцию после минимальной, заведомо рабочей подготовки.
- Таймаут/падение/неполный вывод не равны BSL-исключению. Разбирай журнал и частичный
  JSON; после зависания повторяй конкретный кейс в новой базе/процессе. Не добавляй
  известный таймаут как успешный результат универсального сравнения.
- Проверяй доверенный код проекта. Стенд изолирует базу, но не является песочницей
  файловой системы или сети для исполняемого BSL. Используй только собственные
  временные файлы/локальные тестовые сервисы. Не запускай массовый `pkill`; при сбое
  работай только с процессами, принадлежащими своему запуску.
- Готовый native-адаптер проверен на macOS с учебной 1С 8.3.27.1606 и русским
  шаблоном конфигурации. Для Linux и Windows поиск платформы, кавычки в строке
  соединения и запуск без графической сессии (на Linux, возможно, понадобится
  `xvfb-run python3 …`) заложены по соглашениям, но на настоящей платформе не
  проверялись. Другая ОС, версия или язык требуют проверки адаптера;
  недоступную платформу не заменяй незаметно сохранённым JSON.
